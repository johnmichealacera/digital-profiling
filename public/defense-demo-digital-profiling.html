Scene 0 · Authentication

Login & Role-Based Access Enforcement

S
Barangay Secretary
secretary@barangaytaruc.gov.ph
secretary
Pages: /login/dashboard
The login page enforces credential-based authentication. Each successful login routes the user to a dashboard filtered by their assigned role — no two roles see the same interface.
Actions
1
Navigate to /login → enter secretary@barangaytaruc.gov.ph / staff123 → click Sign In
2
Redirected to /dashboard — sidebar shows only: Residents, Households, Documents, Blotter, Officials, Reports
3
Manually type /budget in the browser URL bar → middleware intercepts and redirects back to /dashboard with no error page
4
Sign out → log in as treasurer@barangaytaruc.gov.ph → sidebar now shows Budget module; Residents tab is read-only
RBAC in action
Each of the 6 roles (Super Admin, Barangay Admin, Captain, Secretary, Treasurer, Kagawad, SK Chairman) receives a uniquely filtered sidebar and dashboard. Permission checks run at two layers: Next.js middleware protects page routes, and every API route re-validates the session server-side — bypassing the UI is impossible.

Households are the geographic unit of the barangay — each one links to a purok, a GPS coordinate (for the map), and a list of residents with their relationship to the household head.
Actions
1
Go to /households → card grid shows: house no., purok, member count, household head name
2
Click House #12 → detail page shows members table, housing profile: type, roof material, wall material, water source, toilet facility, GPS, 4Ps status
3
Click Add Member → search dialog → type "dela cruz" → Juan Dela Cruz appears from the resident database
4
Select relationship "Son" → Add → member appears in the household table, member count increments
5
Click the UserMinus icon → confirm dialog → member unlinked — resident record is preserved, household link is cleared
RBAC in action
Adding or removing household members requires households:update permission (Secretary, Captain, Super Admin). Deleting an entire household requires households:delete (Super Admin and Barangay Admin only) — and only when the household has no active members remaining.

PDF generation in action
PDFs are generated server-side using pdf-lib. The system fetches resident data from the database, fills in the certificate template with the correct legal text, assigns a unique control number, and streams the result to an invisible iframe — triggering the OS print dialog directly without a save prompt.

Safeguards in action
The system prevents two critical mistakes: (1) an admin cannot delete their own account, and (2) the last active Super Admin cannot be deleted or deactivated — the API enforces these rules server-side regardless of what is submitted from the UI.
